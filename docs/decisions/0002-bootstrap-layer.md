# 0002. Слой bootstrap: облако, сервисный аккаунт и хранилище state

**Статус:** принято
**Дата:** 2026-10-15

## Контекст

Инфраструктура должна разворачиваться с нуля кодом, без ручных действий в консоли.
Но Terraform должен от кого-то получить права, а облака ещё нет.
Полностью автоматизировать нельзя: в начале цепочки прав всегда стоит человек.

## Решение

Отдельная конфигурация `terraform/bootstrap`. Запускается от личного аккаунта
владельца организации и создаёт 9 ресурсов:

| Ресурс | Зачем |
|---|---|
| `yandex_resourcemanager_cloud` | Облако проекта |
| `yandex_billing_cloud_binding` | Привязка облака к платёжному аккаунту |
| `yandex_resourcemanager_folder` (`prod`) | Каталог для ресурсов проекта |
| `yandex_iam_service_account` (`terraform`) | От его имени работают остальные слои |
| `yandex_resourcemanager_folder_iam_member` | Роль `admin` аккаунту на каталог |
| `yandex_iam_service_account_static_access_key` | S3-ключ: доступ к бакету со state |
| `yandex_iam_service_account_key` | Авторизованный ключ: доступ к API облака |
| `local_sensitive_file` | Авторизованный ключ в `~/.yc/crm-k8s-iac-sa.json` |
| `yandex_storage_bucket` | Бакет для state слоя prod, с версионированием |

### Порядок создания и depends_on

Terraform строит порядок по ссылкам между ресурсами. Где данных друг от друга
не нужно, но порядок важен, он задан явно:

- каталог `depends_on` привязке к биллингу: в неоплачиваемом облаке
  ресурсы не создаются;
- бакет `depends_on` роли `admin`: бакет создаётся от имени сервисного аккаунта,
  а до выдачи роли у аккаунта нет прав.

### Почему роль admin и почему на каталог

- `admin`, а не `editor`: слою prod нужно создавать сервисные аккаунты
  (например, для нод) и выдавать им роли, а `editor` раздавать права не умеет.
- На каталог, а не на облако или организацию: аккаунт управляет только ресурсами
  проекта. Если ключ утечёт, ущерб ограничен одним каталогом.

### Два ключа сервисного аккаунта

| Ключ | Протокол | Для чего |
|---|---|---|
| Статический | S3 | Backend читает и пишет state в бакете |
| Авторизованный | API Yandex Cloud | Провайдер `yandex` создаёт ресурсы |

### Входные данные

| Что | Откуда |
|---|---|
| `organization_id` | `yc organization-manager organization list` |
| `billing_account_id` | Billing REST API (в `yc` нет команды для биллинга) |
| `project` | Переменная, по умолчанию имя проекта; используется в имени облака и бакета |

Значения собирает `scripts/env-bootstrap.sh` и передаёт через `TF_VAR_*`.
В репозитории нет ни ID аккаунта, ни секретов.

## Последствия

- Личный аккаунт используется только здесь. Остальные слои работают
  от сервисного аккаунта (см. [0003](0003-layers-and-credentials.md)).
- State bootstrap хранится **локально** и не попадает в git: в нём лежат
  приватный ключ сервисного аккаунта и секретный S3-ключ.
  Если state потерять, Terraform «забудет» созданное; восстановить можно
  через `terraform import`.
- Если state или ключ попадут в публичный репозиторий, удалить файл недостаточно:
  ключи нужно перевыпустить (`terraform apply -replace=...`).
- Файл авторизованного ключа содержит 4 поля (`id`, `service_account_id`,
  `public_key`, `private_key`). Стандартный файл от `yc iam key create`
  содержит ещё `created_at` и `key_algorithm`; если какой-то инструмент
  не примет файл, начать проверку отсюда.
- Удаление облака в Yandex Cloud отложенное: имя может долго оставаться занятым.
  Поэтому имя задаётся переменной `project` и меняется без правки кода.
